## D-149 — Pull requests go through one approval queue; each decision is its own file

**2026-10-11.** **Status:** Decided by the operator, implemented
**Spec:** [34 §4.3, §5, §6.1](../../specs/34-duties-delegation-and-independent-approval.md) ·
runbook: [approvals.md](../approvals.md#the-approval-queue)

**The operator's decisions (2026-10-11).**

1. "Queue script + agent reviewer: a one-command queue does the waiting,
   rebasing and merging. A delegated, fresh-context reviewer agent, never the
   author, approves production and routine PRs, with sampled spot-checks for
   you. Governance PRs still come to you, batched into a single prompt."
2. One file per decision. From D-137 on, a decision is
   `docs/decisions/D-nnn-<slug>.md`, and `docs/DECISIONS.md` becomes the
   index. This is the first such file.

**What shipped: the queue.**
- `scripts/approval-queue.ps1` takes an ordered list of PRs (or `-All`, oldest
  first) through rounds:
  1. bring each conflicting PR up to date;
  2. simulate the round's squash merges, so no decision is spent on a head the
     round itself will replace;
  3. wait for the platform's request on each head;
  4. decide;
  5. squash-merge on a green `independent-review`.

  Governance, and anything the reviewer cannot take, comes to the operator in
  one batch per round. The queue never approves as an agent. For a delegable
  tier it calls `POST /api/approvals/{id}/independent-review`, and the platform
  starts the reviewer, mints its `platform_started` credential and records the
  decision through `engine.decide`. The queue's pure logic is in
  `scripts/approval_queue.py`, tested by `test_approval_queue.py`.
- `scripts/enable-agent-reviewer.ps1` proposes a delegation for
  `pull_request_merge`, tiers production and routine (never governance),
  sampling 0.2, 30 days. After the cooling-off it approves the delegation,
  then switches `MYKRONOS_REVIEWER_MODE` to `live`.
- Compose now passes `MYKRONOS_REVIEWER_MODE`, `_MODEL` and `_API_KEY`. None
  of them was listed, so the deployed stack's reviewer could not get a key or
  be switched to live. `ANTHROPIC_API_KEY`, the fallback `reviewer.api_key`
  reads, is still not passed: the reviewer's key is its own.
- The queue scripts are `governance` in `change_classes`. They are the
  operator's approval tooling, and one of them grants delegations. Without
  that, the PR adding them would have computed as `production`, approvable by
  the reviewer it enables.

**What shipped: decisions as files.**
- `docs/DECISIONS.md` keeps D-001 to D-136 untouched. Its header now says how
  to record a decision, followed by a list of `docs/decisions/` generated by
  `scripts/decisions_index.py`. `--check` fails on a stale list, and
  `test_decisions_log.py` runs that check. The same test refuses:
  - a number used twice across the log and the directory;
  - a file whose heading number is not its filename's;
  - an entry with no reasoning in it: the body must pass D-130's rationale
    rule.
- **The transition.** #770, #773, #774, #775 and #777 append D-137 to D-151
  to `docs/DECISIONS.md`. They are not rewritten. The index lists files only,
  so it does not go stale as each of those PRs merges, and the numbering test
  reads both places. `scripts/move-decisions-to-files.py` moves every in-file
  entry from D-137 on into its own file, with its links re-rooted, and
  regenerates the index. A later PR runs it once, after those PRs are in.
  Until then, the queue's union merge still covers the log.

**Why one file per decision.** Union only helps a local merge. GitHub's merge
button runs no merge driver, so two open PRs that both appended to one file
always conflicted on GitHub. Each merge re-headed the next PR, which cost a
request cycle and a second decision. Two new files never conflict.

**What still conflicts.** The generated index lists every file, so two open
PRs that each add a decision both edit its last lines, and GitHub still sees
that as a conflict. That is far fewer PRs than before (only those that add a
decision, not every PR that appended to the log), and the resolution is
mechanical: the queue regenerates the index when it merges main in, rather
than trusting union. A list nobody commits (generated on read) would remove
the conflict entirely, at the cost of the index the operator asked for in
`docs/DECISIONS.md`.

**Why the queue merges main in rather than rebasing.** Measured on #770 and
#773 before writing it: a rebase replays the branch one commit at a time.
#770 appended `D-136` and later renamed it `D-137`, and union kept both
headings; the check caught it. One merge of the final trees applies union
once. Made from main's side ("ours" = main), it writes main's entries first
and the branch's after them. The merge descends from the PR head, so the push
is a fast-forward, and the squash merge discards it.

**What the union check requires.** Main's headings intact and first. The
branch's new numbers unused on main, none twice, and ascending among
themselves. It does not require global numeric order: numbers are taken when
a PR is written and land in merge order, so D-139 already precedes D-137.

**Found on the way.**
- In `live` mode nothing starts the reviewer by itself. `shadow_sweep` runs
  only in `shadow`, and live reviews happen only when the endpoint is called.
  The queue is now that caller.
- A delegation's `constraints` (`max_per_day`, `exclude_paths` in spec 34 §5)
  are stored and never read: `_active_delegation` ignores them. The enable
  script sets none, so it does not imply a limit that is not enforced.

**Rejected.**
- *Renumbering or rewriting the open PRs' entries.* They are other sessions'
  work and nearly merged; the move script handles them afterwards.
- *The queue opening its own requests to skip the ten-minute grace.* The admin
  cannot approve a request opened under the admin identity, and while that
  request exists the job does not open one the admin could approve.
- *Rebasing, as first specified.* It garbles a branch that edits its own
  entry, as measured above.
