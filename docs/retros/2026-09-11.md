# Retro — 2026-09-11: the platform's own reporting path, read the way it reads other people's

No backlog entry closed. Seven were open at the start and seven are open at the
end, and the seven are the same seven. What this run did instead was find
**four ways this platform reported success for something that had not
happened** — the failure it exists to report in other people's CI, four times,
inside itself.

The pattern is not the one the last three retros describe. Those were *turning
a control on is what surfaces the defects behind it*. This one is narrower and
less comfortable: **the code that tells you whether something worked is the
code nothing tells you about when it stops working.** A notifier with no
recipient, a digest that posted nothing, an uploader whose failure was
swallowed by `|| true`, a response saying "No change" about a change it had
just made. Each was silent by construction. Not one was found by a test, and
2,801 of those were passing when the run started.

Three of the four were reachable only by reading a backlog entry or a pipeline
comment and asking whether the thing it described was still true.

## What went well

- **A bug was found before it could fire, in code shipped hours earlier.**
  #238 put two tools on one `sast` capability, which is the entire point of
  B-051 — CodeQL implements no shell language, so ShellCheck runs alongside it.
  Absence reconciliation partitions on `(repo, capability, branch)`. Two CodeQL
  runs are therefore two qualifying `sast` scans, and every ShellCheck finding
  is absent from both, because CodeQL cannot see shell and never could. They
  would have closed as `fixed`. Latent rather than live, because no repository
  has two analysers enabled yet — it would have fired on the day somebody did
  what B-051 asks.

- **Every regression test was checked by reverting the fix.** Four of seven for
  the uploader, three of five for reconciliation, three of four for the digest.
  A test that passes both ways is worth nothing and looks identical to one that
  works. Two of them were passing for the wrong reason until that check: a
  reconciliation test used two findings differing only by title, and the
  finding id is a fingerprint of `rule_id` and `file_path`, so they were one
  finding.

- **The digest bug was demonstrated rather than argued.** `SlackNotifier.send`
  is a coroutine; `send_all` called it without awaiting. Rather than reason
  about it, the real class was run under `warnings.catch_warnings`:

  ```
  warnings: ["coroutine 'SlackNotifier.send' was never awaited"]
  ```

  The same method was then used on the fix: the un-awaited call was
  reintroduced under both annotations, and mypy reported `Success` under `Any`
  and `[unused-coroutine] Are you missing an await?` under the protocol. One
  line of type is the whole difference, and that is now a measurement rather
  than a claim.

- **The class was guarded, not just the instance.** Two guard tests: no
  parameter with a protocol behind it may be typed `Any`, and no test double
  may answer synchronously where the real class is `async`. The first found
  **six** such parameters, two of which a hand-written sweep had missed because
  those functions pass the object along rather than calling a method on it.

- **The estate's own argument was found and honoured rather than overridden.**
  D-112 says "configure the webhook". The Concourse `slack_alert` anchor
  already argues against webhooks and says why — a webhook's secret lives in
  the URL path, a bot token lives in an `Authorization:` header Vault can
  substitute at egress — and notes the credential is one thehub and
  personal-soc already resolve at team scope. `SlackNotifier` could only speak
  webhook, so the choice was never the operator's to make. It takes either now.
  **D-112 was not amended**; the argument was just made executable.

- **A test written for this exact mistake caught it again.**
  `test_compose_passes_settings` exists because *"a notifier wired everywhere
  except the one process that runs is worse than no notifier: it looks
  configured"* — a lesson learned when `routing_enabled` was set in `.env`,
  deployed, and read `False` in the container. Two new Slack settings absent
  from the compose `environment:` block would have done the same thing, in the
  same module the comment is about. The test is the only reason they are
  wired.

## What went badly

- **A pull request was merged and its content never reached `main`.** #247 was
  based on `fix/reconcile-by-tool` rather than `main`, because #246 was still
  open when it was created. Both then merged in the order that loses the work:
  #246 took that branch into `main`, and #247 merged into a branch `main` had
  already consumed. GitHub reported **both as MERGED**, no conflict and no
  warning, and `grants.py` on `main` had no `strand_tool_findings` in it. It
  took a third pull request, #248, to land work that had already been reviewed
  and approved.

  Stacking was reasonable while #246 was open. Retargeting #247 to `main` the
  moment #246 merged was the step that was missed, and nothing in the tooling
  says so.

- **"Merged" was reported twice for things that were not merged.** #246 was
  described as merged while it was still `OPEN` and `BLOCKED` on the review
  requirement, with `main` unmoved. This was caught only because the next
  action began with `git pull` and the head had not changed. Branch protection
  requires one approving review and the operator is the only reviewer, so every
  pull request sits blocked until they merge it themselves — which makes
  "merged" an intention as often as a fact.

- **A pull request number was stated wrongly in a summary.** The Slack bot work
  was #244; it was reported as #242. The tool output said 244. This is the
  smallest failure here and the same shape as the largest: a claim about what
  happened, made without re-reading what happened.

- **Two defects were shipped by this run and found by this run.** The
  reconciliation bug came from #238, four pull requests earlier. The "No
  change" response came from #247's own wiring. Neither reached the operator,
  and both cost a full extra cycle. Finding your own defect quickly is better
  than not finding it; not shipping it is better still.

- **The stranding note had been attached to one branch of three for as long as
  it had existed.** It was harmless the entire time, because stranding could
  only follow a capability removal and a no-op plan removes no grants.
  Dropping an analyser leaves the capability set alone — so the response landed
  on `already_pending` and said `No change; this is already requested` while a
  finding had just moved to `stranded`. A latent reporting defect that became
  live the moment a new caller reached it, which is the same shape as the
  reconciliation bug one file over.

## Themes

**A reporting path has no second reporter.** When a scan lane breaks, the
coverage cross-check notices. When the thing that *does the noticing* breaks,
nothing is upstream of it. The digest logged `Weekly digest sent to 4 owner(s)`
for a job that had never delivered anything; the uploader's failure to open a
scan run was turned green by `|| true`; the notifier was configured and
addressed to nobody, and startup logged a line only in the case where it
worked. Each of these is a single point with nothing behind it, and each stayed
that way for as long as nobody happened to read it. **L0003 — a check that
cannot report is a check that does not exist — applies to the platform's own
reporting with no softening at all.**

**`Any` is where a contract goes to stop being checked.** The digest bug needed
three things: a coroutine, a caller that did not await it, and a parameter
typed `Any` so mypy was never asked. The third is the one that made it
invisible, and it is the cheapest to remove. `Any` is legitimate here in
plenty of places — scan payloads, DuckDB rows, adapter output. It is not
legitimate on a parameter this codebase already has a protocol for, because
there it is not shorthand; it is the type being declined at exactly the point
where a missing `await` stops being an error and starts being a silent
success.

**A test double that does not match the real contract tests the double.**
`test_send_all_sends_one_per_owner` passed for a job that delivered nothing,
because `Recorder.send` was `def` where `SlackNotifier.send` is `async def`.
The double agreed with the caller's mistake. This is the same failure as
recording intent instead of effect from the 2026-09-05 retro, one layer out:
the test asserted what the code meant to do, against an object built from the
same misunderstanding.

**Adding a dimension to a model breaks every rule that did not have it.**
B-056 taught absence reconciliation to read `branch`, because two `main` scans
were closing findings that only ever existed on `develop`. Adding a second
tool to one capability broke the identical rule one dimension over, and the fix
was character-for-character the same shape — `coalesce(tool_name, '')` beside
`coalesce(branch, '')`, on both sides of the comparison. Then it broke
stranding, which knew about capabilities and not tools, and then the response
sentence, which knew about workflow changes and not config changes. **One new
dimension, three separate places that had quietly assumed it did not exist.**
The question to ask of the next one is not "does this work" but "what else
partitions on the thing I just widened".

**The operator's own reasoning is an artifact worth reading.** The strongest
result here — the bot token — came from no code analysis at all. It came from
reading a comment in a Concourse pipeline that had already worked out why a
webhook is the wrong credential, and noticing that the platform's own notifier
could not do the thing its own pipelines had decided to do. D-112 was written
before that argument existed and had not been revisited since. **A decision
recorded in one file and an argument recorded in another do not reconcile
themselves.**
