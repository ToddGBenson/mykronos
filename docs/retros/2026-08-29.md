# Retro — 2026-08-29: moving three repositories off Concourse, and what the move made visible

The goal was a GitHub Actions pipeline that Mykronos controls and that reports back to it,
for `mykronos`, `keel` and `personal-soc`, with TheHub staying on Concourse. That shipped:
parity for `ToddGBenson/mykronos` now reads **11 capabilities covered under Actions, 11
under Concourse, no capability worse**, and `keel` went from nothing covered on either side
to three under Actions against two under Concourse.

The more useful output is what the migration exposed. Every defect found today was already
in production, green, and silent. Building a check that compares two CI systems is what
made them speakable.

Seven pull requests here (#136, #137, #138, #139, #140, #141, #142), three in other repos
(TheHub #275, keel #75, personal-soc #5), one tag (`v8`), two production deploys, and one
lesson worth promoting ([L0005](../lessons/0005-a-comparison-invents-the-gradient-it-needs.md)).

## What went well

- **Every fix shipped with a test that fails on the state that shipped.** Not asserted —
  demonstrated. The pin guard was run against `@v1`, the ranking test against
  `silent -> not_run`, the packaging test against the Dockerfile with the ENV line deleted.
  Three negative checks, three confirmed failures, three restores.
- **Verifying the artifact before deploying caught a 20-file regression.** The plan was to
  run the resync from the running container with env overrides, skipping the deploy wait.
  Checking first showed the container's templates were one patch version behind main on
  **all fourteen** capabilities — #136's probe retry lives in `_base.yml.j2` and bumps every
  one. That resync would have rewritten 18 files across 4 repos *backwards*, silently
  dropping a fix merged an hour earlier.
- **The backup was taken properly, and immediately proved why.** Copying `mykronos.db`
  alone — which an earlier read in this session had done — misses the write-ahead log. The
  WAL was 218KB. `deploy.ps1`'s migration block documents this trap; reading it first is
  what prevented repeating it.
- **Blocked controls were left blocked.** The production approval, the PR review, and a
  `docker cp` into the running container were each refused by a guardrail. None was worked
  around. The `docker cp` in particular was an instinct this same session had already got
  wrong once and written down.
- **The parity gate did the job it was built for, twice.** It refused to bless keel when
  neither system covered it, and it caught `containers` losing coverage. That the second was
  a false positive does not undo the first.

## What went badly

- **The same escaping trap, four more times.** Writing content through a heredoc mangles a
  backslash-n into a real newline, producing unterminated string literals. It happened in
  `config.py`, in `cli.py`, in the `Dockerfile`, and finally in this retro. It is in the
  project memory. It was hit anyway, and each time cost a broken file and a repair. The
  approach that works — build strings from `chr(10)` and `chr(92)`, use `sed` line surgery,
  or use the file-writing tool — should have been the first move, not the fifth.
- **A phantom chased for twenty minutes.** Parity reported `containers` as REGRESSED. The
  upload had actually succeeded — 150 findings, four HTTP 200s. The DuckDB catalog views
  were stale, and `mykronos compact` cleared it. The evidence that it was fine (a logged
  scan-run id and a 200) was in hand before the theorising started.
- **A working design reported as suspicious.** The containers lane logs
  `"/oracle-policy-v1.yaml": not found` and then `built from context '.'`. That is the
  two-context fallback doing exactly what it exists to do. It was flagged as a defect on
  the first read, and corrected only on the second.
- **Fifty minutes of machine time on a stale test run.** A full local suite was started,
  then five source files were edited underneath it. Its verdict was meaningless before it
  was a third done. CI runs the same suite in three minutes and had already passed on every
  PR. It should have been killed the moment the first edit landed.
- **A lesson number invented rather than looked up.** The spec cited `L0011`; the next free
  id was `L0005`. Caught by checking, but the citation was written first and verified after.
- **`pytest` nearly misdiagnosed as hung again.** The parent process showed 0.10s CPU and
  the conclusion "no worker child, so this is blocked" was already forming. There was a
  child, at 286s. Checking is what saved it; the prior instinct was unchanged.

## Themes

**The second half of a fix is where the bug lives.** D-051 established that the upload
action must be pinned to a commit. It was, repeatedly. The setting immediately beside it —
which installs the same package, into the same job, in a step that runs *first* — was never
looked at and never moved. `pip install` of an already-satisfied requirement is a no-op, so
the older pin won every time and the newer one was decorative. `sast` and `aegis` survived
only because `v1` happened to know those two capability names, which is precisely why it
went unnoticed: it presented as two broken capabilities rather than as a stale pin.

**A gate that detects loss cannot detect absence.** "No capability is worse under Actions"
is a true sentence about two systems that both cover nothing, and on its own it reads as
permission to delete a pipeline. The ranking made it worse by inventing an order inside the
uncovered states — `not_run` above `silent`, because a lane that has not fired sounds more
innocent than one that fires and reports nothing. Innocent was not the question. Covered
was. The verdict now states the absolute before the relative.

**Right in every checkout, wrong in every deployment.** `Path(__file__).parents[2]` is the
repository root from a source tree and the parent of site-packages from an installed wheel.
Two policy files were also never copied into the image. `weights()` catches the error, logs
at WARNING, and returns an empty dict — so every governance score in production was computed
from an empty table, with no failure and a plausible number on the dashboard. No test could
have caught it: the suite runs from a checkout, where the path is right. That is D-052's
shape, one directory over.

**Silence is the shared failure mode.** A pip no-op that downgrades an uploader. A build
failure swallowed into a clean scan of zero images. A `weights()` that returns nothing. A
`not_run` that absorbs `failed`. A promote that has never once run. None of these raised,
none went red, and each was found only by comparing two things that should have agreed.

## Open work, noted

- **Promote is deadlocked.** Every run sits `pending` with no job created. Ruled out:
  concurrency collision, job saturation, deployment branch policy, plan and visibility,
  `prevent_self_review`. Consequence: GHCR `:latest` has never moved, so **`deploy.ps1` is
  a trap** — it would reinstall the old image. Both of today's deploys pulled the sha tag
  and tagged locally. This is the next thing to fix.
- **Parity can read a stale catalog** and report a regression that is not real. The
  false-green was fixed today; this is its mirror and is not.
- **`latest_workflow_runs` reads one repository-wide page** of 100 completed runs, so a
  quiet lane in a busy repo comes back as never-run. Recorded in the client docstring; the
  fix is the per-workflow endpoint for lanes missing from the page.
- **Oracle's `cancel-in-progress: false`** contradicts its own comment: it serialises
  duplicate decisions rather than preventing them. Changing it means cancelling a decision
  mid-write, so it is not a one-line change.
- **`dast` and `functional` fail on both sides.** Pre-existing, and now visible as `failed`
  rather than hidden behind `not_run`.
- **keel's Concourse pipeline can now be retired** on evidence, which was not true this
  morning.
