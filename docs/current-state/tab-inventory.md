## Findings

Ordered by consequence. Each is verified through code and cites its evidence.

### F1 — An unknown `?tab=` value silently renders the Dashboard

`page.tsx` L169–182 is a seven-branch ternary whose final `else` is
`<DashboardTab>`. There is no validation of `query.tab` against `TABS`.

A typo'd, renamed, or removed tab id is therefore **indistinguishable from the
default**. A link to `?tab=supply-chain` (the label) rather than `?tab=sscs`
(the id) lands on Dashboard with no error, and a bookmark to a retired tab
degrades silently.

This is the same class as a defect TheHub fixed twice this week: a sub-tab id
with no matching branch produced a wrong-but-plausible render rather than a
visible failure. **Recommended:** validate `tab` against `TABS` and render
`not-found` (or an `ErrorPanel` naming the bad id) on a miss.

### F2 — No loading state exists anywhere, in a `force-dynamic` app

Verified by exhaustive scan of all 38 `.tsx` files:

| Pattern | Occurrences |
|---|---|
| `ErrorPanel` | 32 |
| `EmptyState` | 21 |
| `Suspense` | **0** |
| `Skeleton` | **0** |
| `loading.tsx` route files | **0** |

Error and empty states are genuinely well covered — this is not a project that
neglects states in general, which makes the loading gap specific rather than
symptomatic. But the repo page is `force-dynamic` and awaits several backend
calls before first paint, so the user sees the *previous* page until the server
responds, with no indication that anything is happening.

`primitives.tsx` exports `ErrorPanel` and `EmptyState` but **no loading
primitive**, so there is nothing for a component to reach for even if it wanted
one.

**Recommended:** add a loading primitive plus `loading.tsx` at
`app/repos/[repoId]/`, which in the App Router gives an instant boundary for
free.

### F3 — One concept, three names, and all eight tabs live inside one file

> **Corrected 2026-08-30.** A first version of this finding said codenames
> "leak into the component layer". That was wrong and the correction changes
> what the finding is. The shared component files are named plainly
> (`decisions.tsx` → `DecisionsTab`, `insider-risk.tsx` → `InsiderRiskTab`) and
> the imports at `page.tsx` L3–L33 use those names with **no aliasing**.

What is actually there: **all eight tab renderers are local `async function`s
defined inside `app/repos/[repoId]/page.tsx`** (L209–L595+), each wrapping the
imported shared component. That is why the file is 607 lines — it carries
routing, page-level data fetching, and eight tab implementations at once.

The naming problem is a consequence. For a single concept there are three names
across three layers:

| UI label | page-local wrapper | shared component / file |
|---|---|---|
| Insider Threat | `AegisTab` | `InsiderRiskTab` / `insider-risk.tsx` |
| Remediation | `PatchworkTab` | `RemediationTab` / `remediation.tsx` |
| Risk Decision | `RiskDecisionsTab` | `DecisionsTab` / `decisions.tsx` |
| Supply chain | `SupplyChainTab` | `SscsTab` / `sscs.tsx` |

Aegis and Patchwork are real codenames elsewhere in the estate
(`.github/workflows/mykronos-aegis.yml`). Cost is search failure: someone
tracing a bug report about "Remediation" finds `remediation.tsx` but not the
`PatchworkTab` wrapper that decides what it receives.

**Recommended:** two separable changes. (a) The codename fix, scoped below.
(b) Extract the eight local wrappers out of `page.tsx` — the file is doing
routing, fetching and eight implementations, and it is the single place every
tab change must touch.

#### F3a — The codename fix, scoped

**Confirmed by the Product Owner 2026-08-30:** Aegis is a codename and should
be changed; it is the CI/CD scan for Insider Threats. Patchwork is the codename
for vulnerability triage management and remediation.

`specs/00-overview-and-glossary.md` is the authority and already pairs every
codename with a plain capability name. Aegis / Atlas / Patchwork are *real
upstream systems* ("Modeled on the existing internal Project Aegis"), so the
codename is legitimate **internally**. The defect is that three of them reach
the user.

**`atlas` already proves the fix.** In `primitives.tsx` `CAPABILITY_META`,
fifteen capabilities each map a key to a label. Twelve labels are plain. Atlas
— itself a codename — is among the clean ones:

```
atlas:     { label: "Dependencies (SCA)" }           ← codename NOT exposed
aegis:     { label: "Insider risk (Aegis)" }         ← exposed
oracle:    { label: "Risk decisions (Oracle)" }      ← exposed
patchwork: { label: "Auto-remediation (Patchwork)" } ← exposed
```

The key stays `atlas`; only the label is plain. Three capabilities did not
follow the precedent that already exists in the same object.

**Three tiers, and they must not be conflated.**

*Tier 1 — user-visible labels and prose. UI-only, no API impact, ~11 sites.*

| File:line | Text |
|---|---|
| `primitives.tsx:144-146` | the three `CAPABILITY_META` labels |
| `primitives.tsx:410` | `title="Oracle is opt-in and has not judged this repository"` |
| `app/page.tsx:60` | `label="Oracle: no go"` |
| `app/page.tsx:106` | table header `"Oracle"` |
| `app/layout.tsx:46` | nav item `"Oracle policy"` |
| `decisions.tsx:44` | `title="Oracle has not judged this repository"` |
| `insider-risk.tsx:137,138` | `"Aegis is BLOCKING / advisory for this repository"` |
| `open-findings.tsx:550` | `title="Patchwork produced a fix for this…"` |
| `remediation.tsx:66` | `title="Patchwork has not run here"` |

*Tier 2 — the capability KEY. Breaking; do not change casually.* `aegis`,
`oracle`, `patchwork` are identifiers the backend, workflows and stored
configuration use (`aegis.py`, `SIGNAL_CAP`, `/api/patchwork/...`,
`scan-health.tsx:23` `NO_SCAN_RUNS`). Occurrence counts across the repo:
Oracle 1922, Patchwork 628, Aegis 424.

*Tier 3 — instructions that deliberately name the key. Correct as-is; changing
them would be a REGRESSION unless Tier 2 changes first.* These are styled
`font-mono` precisely because they are identifiers the user must type or
recognise:

- `page.tsx:122` "No repository has enabled the `oracle`"
- `page.tsx:246` "`oracle` — that is a choice, not a gap"
- `decisions.tsx:47` "Enable the `oracle` capability"
- `insider-risk.tsx:74` "Enable the `aegis` capability"
- `remediation.tsx:69` "Enable the `patchwork` capability"

**Recommended:** Tier 1 only, following the `atlas` precedent. It removes every
codename a user reads, touches no identifier, and needs no backend change.
Tier 2 is a separate decision with a migration cost that should be argued on
its own merits, not carried in on the back of a label fix.

### F4 — Dashboard fetches at page level; the other seven fetch themselves

`DashboardTab` receives eight-plus props (`live`, `scanHealth`,
`scanHealthError`, `ci`, …) resolved in `page.tsx` before render. The other
seven receive only `repoId` (and `query` for Findings).

The page comment explains why — those fetches feed the Built/Scanned-by links
and capability buttons rendered on *every* tab. So this is deliberate, not
accidental. The consequence is still real: **every tab pays for the Dashboard's
fetches**, whether or not it uses them, on a `force-dynamic` page.

**Recommended:** measure it before changing it. If the shared fetches are cheap
this is fine; if not, the shared subset should move behind the layout or a
cached call.

### F5 — Empty states are handled two different ways

All nine top-level pages render lists, and all of them handle emptiness — but
five reach for the `EmptyState` primitive and four hand-roll it.

| Page | `.map()` | zero-checks | uses `EmptyState` |
|---|---|---|---|
| `/` | — | — | yes (2) |
| `/pull-requests` | — | — | yes (2) |
| `/retro` | — | — | yes (2) |
| `/threat-intel` | — | — | yes (2) |
| `/triage` | — | — | yes (2) |
| `/decisions` | 6 | 4 | **no** |
| `/incident` | 3 | 4 | **no** |
| `/remediation` | 2 | 1 | **no** |
| `/trends` | 12 | 4 | **no** |

This is *not* "missing empty states" — an earlier read of the aggregate counts
suggested that, and checking the `.map()` and zero-check counts disproved it.
It is inconsistency: the same state expressed two ways, so a reader cannot tell
from the primitive's absence whether a page handles emptiness or forgot to.

The weakest instance is `trends/page.tsx` L225 —
`if (known.length === 0) return "no data";` — a bare string rather than
markup, with 12 `.map()` calls and 4 zero-checks in the file.

Note `/remediation` has 2 `.map()` calls but only 1 zero-check, so one list
there may render nothing with no message. Not confirmed; worth a look.

**Recommended:** route the four hand-rolled pages through `EmptyState`. The
primitive already exists and is used 21 times, so this is convergence, not new
design.

## Method correction: this product already documents its own "should"

**Found late, and it changes Phase 3.** This repository carries:

- **`specs/` — 33 numbered specifications.** 15 of them (17–31) include an
  **Implementation status** table with per-item values like `Done`,
  `Not planned this pass`, `Plumbing only, off by default`.
- **`docs/DECISIONS.md` — a 3,906-line decision register**, ~65 numbered
  decisions (D-001 … D-063+), each with a trigger and its reasoning.

Spec 18's status table is the model: it records not only what shipped but what
was *reversed* — "shipped once with summary cards + a findings list, reversed
on sight" (D-063) — and what was deliberately skipped rather than approximated:
"noted as an explicit, honest gap, not silently approximated".

**Consequence for the does/should/could analysis.** The generic framework
assumes "should" must be derived. Here it is largely already written, by people
with more context than a code read provides. Deriving it independently would
waste effort and risk contradicting decisions made deliberately.

Phase 3 is therefore a **reconciliation**, not a derivation:

| Column | Source |
|---|---|
| **Does** | Code inspection (this document, extended per surface) |
| **Should** | `specs/` §-level requirements + `DECISIONS.md` |
| **Gap** | Where code and spec disagree, or a spec item has no status |
| **Could** | Items the specs explicitly defer, plus genuinely new proposals — each labeled which it is |

Anything proposed as "could" that a decision already rejected must cite that
decision and argue against it explicitly, rather than re-proposing it as new.

## The information architecture has a principle — do not flatten it

**Resolved from source, 2026-08-30.** `/remediation` and `/decisions` exist as
both top-level pages and repo tabs. They are **not duplicates**. The split is
portfolio-wide vs repo-scoped, and the source documents the reasoning at both
sites:

`app/decisions/page.tsx`:

> Oracle, portfolio-wide. Three things a per-repo decision list cannot show:
> who is worst right now, what blocking mode would have cost had it been on,
> and the policy every score was produced from. The last one is here rather
> than buried in the repo because a scoring rule you have to go looking for is
> one people assume is arbitrary.

`app/remediation/page.tsx`:

> Ten repositories with the same unpinned dependency means ten draft pull
> requests … one pull request touching ten repositories would bypass per-repo
> review and CODEOWNERS, which is most of what makes a draft pull request
> reviewable.

So the IA answers two different questions at two altitudes: *"what is true
across the estate"* (top-level pages) and *"what is true for this repository"*
(repo tabs). The portfolio level additionally carries the things that are
**incoherent per-repo** — cross-repo ranking, counterfactual cost, and the
governing policy.

**This matters for Phase 5.** A future-state proposal that merged the two
levels for tidiness would destroy a deliberate distinction whose rationale is
already written down. Any IA recommendation must state explicitly what happens
to the portfolio/repo split, and justify a change against these two comments.
